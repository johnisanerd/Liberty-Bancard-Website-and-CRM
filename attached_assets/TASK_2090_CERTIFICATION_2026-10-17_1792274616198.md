## Findings requiring completion

### 1. Lookup outcomes are fingerprinted against settlement-time inputs

**Priority: high. Source-confirmed correctness gap; no PostgreSQL interleaving reproduced here.**

`claimSerperLookup()` stores a token and expiry, but does not capture the lookup's input fingerprint. The waterfall sends the selected target's name and address to the provider. Later, `recordSerperLookupOutcome()` computes its fingerprint from the then-current `businesses` row.

For example:

1. A lookup is dispatched for name/address A.
2. Its settlement transaction completes.
3. The business changes to name/address B before the separate memory update.
4. The old A outcome is saved with B's fingerprint.

The memory entry can then exclude a lookup of B for the negative-result TTL, despite the promise that changed inputs reopen discovery. Provider settlement fencing does not make the later separate memory update atomic with the original inputs.

**Correction:** pin the exact lookup-input fingerprint with the claim/request and record that fingerprint with its outcome. Compare current inputs against the pinned inputs when applying exclusion. An old result must not become a negative result for newly changed inputs.

**Required regression:** change inputs while the lookup is in flight and between settlement and memory writing; demonstrate that the old outcome cannot suppress the new inputs. Preserve token fencing and the single-purchase claim behavior.

### 2. Unlabeled request allowances do not implement the promised hard credit cap

**Priority: high before any bounded registry measurement. Independently reproduced pure-function failures.**

The implementation is request-bounded. Its optional `dailyReportedCredits` check observes credits after requests settle; it does not reserve the maximum credit charge for the next request.

The exact allowance function permits:

| Case | Observed behavior |
| --- | --- |
| Credit cap 10, already reported 9, next request charges 3 | Request is authorized; total becomes **12** before later requests stop |
| Provider omits reported credits | Request counts increase, but reported-credit usage increases by **0** and further requests remain possible |
| Daily request cap 1; two independent runs read usage 0 | Both allowance objects authorize a request |
| Positive request caps with no credit cap | Gate enables successfully; credit cap remains null |

Daily usage is read from attempt telemetry; the telemetry writer intentionally swallows write failures. This is useful diagnostic data, but is insufficient as the sole durable spending authority. A per-business claim does not serialize allowances across different businesses.

**Correction:** enforce the measurement's approved credit allowance through durable, shared reservation and settlement accounting for every physical request. Use documented or explicitly measured conservative endpoint charging bounds when reserving; do not infer a universal multiplier from unmatched dashboard totals. Missing charge information must remain unknown and conservatively reserved, rather than silently becoming zero available-spend impact. Coordinate parallel runs against the same allowance.

If a hard actual-credit ceiling cannot yet be demonstrated, leave the unlabeled measurement inactive and certify only the request-limited mechanism. Existing ordinary Serper discovery need not be paused for this correction.

**Required regressions:** next-request overshoot, missing charge fields, failed telemetry writes, concurrent runs on different businesses, retries, and a lookup's second request. Demonstrate that the approved cap cannot be exceeded through those schedules.

### 3. Allowance-stopped runs overstate processed work

**Priority: medium. Source-confirmed status/accounting gap.**

The new allowance check can break out of the target loop before every selected business is attempted. However, the final stage update and return value use `targets.length` as the processed count and mark the run completed whenever the failure count is zero.

Thus a run that selects multiple businesses and exhausts its allowance after one request can report the entire selected population as processed. Memory-skipped candidates are also included in that number. This repeats the distinction the CRM must make between a completed queue invocation and completed business work.

**Correction:** retain selected count separately; count actually attempted, memory-skipped, completed and allowance-deferred work explicitly. Record the stop reason and use status semantics that cannot imply every selected business was processed.

**Required regression:** select several eligible businesses with a one-request allowance. Prove truthful counts, a visible allowance-stop reason, preservation of unfinished work and successful continuation under a fresh ordinary run key without duplicate effects.

Document the exact original key, request parameters, stored snapshot and mismatch cause; demonstrate that a genuine same-payload completed replay returns without another purchase. Distinguish this from a changed request under the same key, which should be rejected. The new certification's “second pass” uses a different key and does not establish completed-key replay.

The approved numeric cap must be enforced by the corrected mechanism before any live measurement. No live measurement or provider spend was authorized or performed during this review.
