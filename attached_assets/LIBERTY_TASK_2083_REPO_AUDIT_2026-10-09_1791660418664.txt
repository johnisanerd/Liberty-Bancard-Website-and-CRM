B. SHARED DOMAIN MATCHING CAN ABSORB OR BLOCK A SEPARATE LOCATION

Confirmed source:
  server/services/organization-resolver.ts — resolveOrganization and peekOrganizationResolution.
  server/services/canonical-provider-import.ts — organizationInput and later stableKey construction.

resolveOrganization retrieves candidates using OR across source identity, place ID, domain and phone. With exactly one candidate it checks conflicting nonempty place IDs/domains/phones, but does not compare city, state, address or company name before returning matched.

Consequently, an existing branch and incoming different-location record sharing only the brand domain can be matched despite their location difference. When both have different place IDs, the existing branch found through the shared domain causes a hold; the resolver does not establish that a sufficiently supported second branch should be created. Multiple branches sharing a domain also enter the ambiguous candidate set even when one has stronger exact identity evidence.

The resolver supports sourceIdentity, but this provider importer does not pass it. It constructs its source identity only after organization resolution. The preview function also lacks the sourceIdentity input, so it cannot represent that future exact-source transition without an additive change.

Required amendment:
Define exact source/location identity precedence and contradiction handling. A shared brand domain supplies candidate evidence, not ownership of every location. Pass supported source identity before resolution and retain transactional deduplication across all relevant identifiers. Permit one supported new location when evidence distinguishes it from existing branches. Preserve real ambiguity, rather than forcing a winner. Keep preview and write decisions aligned for the same supported input.

Acceptance examples:
Different-city locations sharing a domain are not silently merged. A distinct supported place/location is created once. Exact existing source identity is not defeated merely by unrelated same-brand domain candidates. Concurrent equivalent intake remains idempotent; genuine contradictory identifiers remain held.

This is source control-flow analysis, not an executed database concurrency result.

D. A BRIDGE GUARD FAILURE BEFORE CLAIM COMMIT CAN REPEATEDLY STOP THE RECOVERY TICK

Confirmed source:
  server/services/canonical-import-recovery-worker.ts — import_cursor_claim transaction.
  server/services/provider-import-identity.ts — verifyProviderImportIdentity and assertBridgeEvidenceNativeGuard.
  server/services/canonical-import-recovery-outcomes.ts — guard/authority failures remain fatal.
  scripts/certification/test-audited-retained-import-recovery.ts — disabled-guard negative test.

The row claim transaction updates the selected item, then verifies/creates the retained identity bridge, then writes the durable claim receipt. The per-row processing catch starts only after that transaction succeeds.

A missing bridge guard therefore aborts before that catch. The lease update and fairness receipt roll back. The same selected bridge-dependent original can be selected again on a later tick while another non-bridge original remains eligible in the same worker. Existing round-robin fairness relies on committed claims and does not by itself solve this failure.

The existing certification source proves that disabling the guard fails closed. That is valuable, but does not prove another eligible row progresses under the same missing-bridge topology.

Required amendment:
Implement explicit isolation of the affected native/source capability within the existing recovery authority. Preserve an honest blocked diagnosis and keep the original row/evidence unchanged. Eligible work that does not require the missing capability must still get an ordinary committed opportunity. Do not classify owner/guard failures as generic retryable row failures, manufacture fulfillment, skip bridge verification or continue uncertain commits.

Acceptance example:
With general relationship guards valid but the bridge guard absent, mix a bridge-dependent original with a non-bridge eligible original. The former remains safely blocked and diagnosable; the latter progresses. Independent linking/local stages also continue when their own authority is valid. Restore the bridge through the supported native-delivery path and prove the original becomes recoverable without a new upload or duplicate evidence.

The exact Dev/Prod object mismatch must be freshly measured. Migration text is not installed-function proof.

E. ORDINARY UPLOAD FAILURE CLEANUP CAN MARK THE WRONG IMPORT FAILED

Confirmed source:
  server/routes/imports.ts — POST /api/leads/import-csv catch.
  server/services/import-execution.ts.
  server/services/csv-import-processor.ts.
  server/services/csv-import-recovery.ts.
  server/index.ts — startup reconciliation.

The upload error handler fetches all CSV imports and marks the first one whose status is processing as failed. It does not identify that record through the failing request's execution/import identity. A failed upload or pre-processing request can therefore mark another concurrent upload's UI projection as failed.

Also, resumeExpiredCsvImports processes executions sequentially without an execution-level catch. Its startup caller catches an escaped error for the whole reconciliation invocation and says it will retry on the next restart. That invocation can abandon later candidates after one execution fails. The build must establish sustained ordinary recovery, rather than using another restart as routine operation.

Correction to avoid a false finding:
A request-free fallback processor exists. processPersistedCsvImport calls recoverPersistedCsvImport when no interactive processor is registered, and provider formats use the canonical provider writer. Registration inside the upload handler does not prove fresh-process recovery is missing. Test that existing path; do not add a replacement recovery factory.

Required amendment:
Bind cleanup/status projection to the exact durable execution/import and current authority. Refuse to mark an unrelated processing import failed. Preserve primary/cleanup errors and uncertain-commit handling. Within the existing recovery scheduling authority, ensure a safely isolated failing execution does not abandon other eligible executions and explain how due work continues without customer restarts.

Add these entry points to Relevant files, alongside the existing retained-recovery files.

Acceptance examples:
Two simultaneous imports plus a malformed/failed third request cannot alter the wrong import. A fresh process resumes an expired ordinary upload through its persisted source/coordinates. Failure in one recoverable execution does not suppress another execution's eligible progress. Replay and crash boundaries create no duplicate contacts, businesses, links or row outcomes.
