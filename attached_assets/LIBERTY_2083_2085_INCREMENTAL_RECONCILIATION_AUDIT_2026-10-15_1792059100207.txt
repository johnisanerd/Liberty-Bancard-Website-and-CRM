FINDING 1 — LIMIT DOES NOT BOUND THE EXPENSIVE CHANGE SELECTION

Priority: Required for the repair.
Source:
  server/services/contact-business-evidence-page.ts:18–51
  server/services/contact-business-evidence-candidates.ts
  migrations/0356_contact_linker_indexed_domain.sql

loadEvidenceRelationshipPage requests 25 contacts plus a lookahead, but first applies an OR across:
- contact updated_at;
- new contact source events;
- changed canonical source links joined to businesses, using normalized names/domains or retained identifiers;
- Sunbiz entity revisions and identity matches;
- changed businesses.

These predicates are in WHERE before ORDER BY/LIMIT. A result limit of 26 does not cap the number of contacts or registry/source candidates examined to find those results.

The Sunbiz revision check additionally extracts updated_at through to_jsonb(changed_entity), although shared/schema.ts declares a typed updated_at column. This is a concrete expression to investigate in the exact plan; changing it alone is not a proven repair.

The candidate retrieval CTE used AFTER selection already contains bounded contact IDs and parameterized lateral lookups. Earlier successful candidate timings therefore do not certify the incremental selection statement. Repairing or benchmarking that CTE again would miss the current first-stage risk.

Safe direction:
Read an ordered bounded raw contact-ID page independently of expensive change predicates, then evaluate changes only for that page using relevant indexed identity/source probes. Keep raw page size, lookahead and evidence hydration explicit. Reuse the already introduced normalized identity indexes where their expression and partial predicate actually match.

A bounded query is not automatically fast: each bounded contact must still avoid unindexed full-registry probes. Require the actual selector and hydration plans, not just a generic EXPLAIN or another pool-size change.

No fresh production plan was executed here, so the supplied “full scans” and approximately 30-second cancellations are not newly reproduced performance measurements.

FINDING 2 — AN OLD SOURCE IDENTIFIER CAN BYPASS THE CHANGE TIMESTAMP

Priority: Fix in the same selector.
Source:
  server/services/contact-business-evidence-page.ts:33–42

The changed-link WHERE has this logical shape:
  (link_revision >= changedSince AND business/name/domain_match)
  OR retained_source_identifier_match

The retained-identifier EXISTS is outside the timestamp-qualified group. SQL AND precedence means a matching historical filing/place key can admit an unchanged source link. This can repeatedly select otherwise unchanged contacts and overstate changed work. It is a false-positive change-selection defect; it does not establish authority to link a business.

Apply the intended timestamp condition to the relevant identifier alternative too, while keeping genuinely new contact-source events eligible through their own branch. Do not remove the retained identifier route to improve speed.

Parity requirement:
Preserve all legitimately changed candidates and the evidence/writer outcomes. Exact byte-for-byte selector parity with this false-positive behavior is not the goal. Record the deliberate correction and test old unchanged identifiers separately from fresh source-only changes.

FINDING 3 — THE CURRENT WORKER CANNOT SAFELY CONSUME AN EMPTY BOUNDED PAGE

Priority: Coordinated loader/preview/worker change.
Source:
  server/services/contact-business-evidence-page.ts:119–125
  server/services/contact-business-system-links.ts:263–271
  server/services/contact-link-automation.ts:128–142, 197–205, 219–227

Today the loader returns the last selected changed contact, and preview.nextCursor depends on whether another selected contact exists. The worker advances per processed candidate and unconditionally sets complete=true when preview.rows is empty.

That is valid only while an empty selector result means there are no changed contacts anywhere beyond the cursor. After bounding raw IDs first, an empty changed list can mean merely “none of these inspected IDs changed,” with later IDs still pending.

Executed probe:
The actual worker was supplied a hypothetical bounded page with rows=[], later inspected IDs, and a non-null continuation. It marked the pass complete and left its cursor at 10. This proves that changing the loader alone would be unsafe. It is not a claim that the current unmodified loader returns that hypothetical contract in production.

Required additive page semantics:
- inspected-through raw ID and a reliable pass-exhaustion/lookahead result;
- changed/evidence rows within that inspected scope;
- checkpoint advancement across unchanged IDs;
- no advancement past a changed candidate whose processing did not complete;
- end-of-pass only when the inspected population is actually exhausted.

The existing deadline protection for an unprocessed nonempty tail worked in the source probe and must survive the repair.

Keep current completed-initial-pass status, run identity, cumulative counters, operator pause and live lease/token authority. A raw inspected-page cursor is not an assignment count. Do not add inspected unchanged contacts to “held” merely to make counters advance.

FINDING 4 — PRESERVE THE CHANGE WINDOW UNTIL THAT PASS IS EXHAUSTED

Priority: Required regression boundary, not a separate project.
Source:
  server/services/contact-link-automation.ts:128–136, 197–227

The existing worker rolls changedSince forward only when starting the next pass, using the previous scanStartedAt. This lets later changes behind the ID cursor be considered in a subsequent pass.

The proposed paging change must preserve that window through empty pages, sparse results, restarts, failed queries and partial processing. Do not set changedSince to publication time or current wall time to escape the timeout. Do not reset the completed initial pass or rewrite the saved cursor to a guessed value.

Capture the current stored state before implementation/publication. Continue the actual saved incremental state. The existing automatic rollover between incremental passes can start its next ID traversal normally; that is different from manually restarting the initial backfill.

Test an initially unchanged page, a later changed contact, a source-only change, a change behind the current cursor and restart at each checkpoint boundary. Include concurrent evidence updates and prove the chosen revision/window semantics do not lose work.
